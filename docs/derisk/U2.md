## Approach (D15): the stack is baked into the container IMAGE

Per decision D15, the brain stack is built into a **custom sandbox image** at
`docker build` time (as root), not installed into the running container. The
OpenShell sandbox runs as the unprivileged `sandbox` user (uid 998, no root /
sudo), so installing Postgres/pgvector into the live container is the wrong
pattern — the environment belongs to the image definition. In OpenShell
v0.0.116, `sandbox create --from` does not build a local Dockerfile itself; the
flow is `docker build -t <image>` with the gateway's engine, then
`openshell sandbox create --from <image>`.

- **`docker/phase1-brain.Dockerfile`** — `FROM
  ghcr.io/nvidia/openshell-community/sandboxes/base:latest` (the proven
  prime-claw base), installs `postgresql-16` + `postgresql-16-pgvector` (Ubuntu
  noble repos) and compiles the `gbrain` CLI from the operator's local zbrain
  checkout with Bun. Built as `prime-claw-brain:0.1.0`.
- **`scripts/apply-phase1-brain.sh`** — stages the gbrain build context, builds
  the image, recreates the sandbox `--from` it, `--upload`s the brain repo
  folder to `/sandbox/brain`, and initdb+starts Postgres as the sandbox user.
- **`scripts/check-phase1-brain.sh`** / **`scripts/validate-phase1-brain.py`** —
  readiness gate / acceptance.

## The agent owns its Postgres

Per the explicit requirement: the in-sandbox agent owns its own Postgres.
- **PGDATA = `/sandbox/pgdata`** (the sandbox-owned read-write path), `chmod 700`.
- The `sandbox` user runs `initdb`, `pg_ctl start|stop|status`, `psql`,
  `createdb`, and `CREATE EXTENSION vector` itself — **no root, no sudo**.
- Superuser role `gbrain` with trust auth on localhost.
- **Socket dir = `/sandbox`** (`-c unix_socket_directories=/sandbox`): the
  OpenShell filesystem policy makes `/var` read-only at runtime, so the default
  `/var/run/postgresql` socket dir is not writable; the socket is placed in the
  sandbox-owned path instead. The image `chown` of `/var/run/postgresql` does
  not survive the runtime read-only mount.

## Findings / notes

- **gbrain is built from source (not published).** The CLI is the Zendesk
  `zbrain` fork; the image compiles it with `bun build --compile`.
- **Upstream break (recorded, not fixed here):** the zbrain fork deleted
  `templates/` (commit `a68893077`, "strip upstream cruft") while
  `src/core/bootstrap/assets.ts` still imports `templates/bootstrap/*`, so a
  fresh zbrain checkout **cannot compile gbrain**. The spike restores
  `templates/` from git history (`d337920c1`) into the staged build context
  only — the operator's zbrain working tree is untouched. Fidelity note: the
  restored template assets are from ~v0.47 while the source is v0.49.0.0; the
  bootstrap templates affect `gbrain init`/onboarding scaffolding, not the
  search/query/serve path under test, so the U2 verdict is unaffected. **The
  zbrain repo should either restore `templates/` or remove the dead imports.**
- **pgvector version:** in-sandbox 0.6.0 (Ubuntu noble) vs the reference
  brain-daemon's 0.8.2 (PGDG). gbrain warns HALFVEC is unavailable below 0.7 but
  reports "functionality otherwise identical" (VECTOR(1536) fallback). Adequate
  for the spike; pin 0.8.x via PGDG if HALFVEC is needed later.
- **R-U2-5 mechanism:** the sandbox binds its own `localhost`; host exposure is
  via `openshell sandbox create --forward <hostport>:5433` (host `:5433` is
  currently held by the reference `brain-daemon-ralph-pva`). Non-blocking.

## Embedding through the gateway (R-U2-6)

gbrain embeds via the **same OpenShell L7 placeholder mechanism** as the
prime-agent credential proof (Slice 3): the sandbox holds only the
`openshell:resolve:env:...` placeholder in `OPENAI_API_KEY`; the
`prime-claw-ai-gateway` provider substitutes the real shared gateway key at L7.
The key never touches sandbox disk. Config: `provider_base_urls.openai =
https://ai-gateway.zende.sk/v1` (+ `OPENAI_BASE_URL`), `embedding_model =
openai:text-embedding-3-large` (1536-dim), matching the host gbrain config.

**Root cause worth recording:** the sandboxed gbrain embed initially returned
"Forbidden" even though identical `curl`/node fetches to the gateway returned
200. The cause was the **OpenShell egress policy**, not the gateway: gbrain is a
compiled **Bun** binary, and Bun's fetch runs under the `bun` binary identity,
which was not in the policy's `model_ai_gateway` `binaries` list — so the proxy
denied it (`policy_denied: binary '/usr/local/bin/bun' not permitted`). Adding
`/usr/local/bin/bun` (and `/usr/local/bin/gbrain`) to the endpoint's `binaries`
fixed it. Lesson: **the L7 policy keys credentialed endpoints per calling
binary; any new runtime that must reach a credentialed endpoint must be bound
explicitly.** (Also: provider env injection happens at sandbox *create*, not
per-exec — a post-hoc `provider attach` requires a sandbox restart.)

**Provider attach ordering:** attach the AI Gateway provider at `sandbox create`
(`--provider`) so the placeholder env is injected into the main process; the
apply script does this.
