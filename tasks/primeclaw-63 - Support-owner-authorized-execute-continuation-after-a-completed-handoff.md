## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
## Outcome and authority
Support a narrowly bounded, owner-led continuation of the SAME task-native Episode after its canonical handoff was received and completed but the following execute delivery failed or remains historically unproved. Do not strand useful work merely because the historical chain cannot be reconstructed. Joe's design-only decision, relayed by Task-2 Manager, is explicit: “Yes, this is clearly NOT double delivery, it's recovery from a failed delivery. We need that use case covered!”

This is a separate proposed change to REQUIREMENTS.md P15 and editable continuation policy, not a reopening of Done PRIMECLAW-62. The current specification-authoring authority permits design/review/publication ONLY. It does not authorize planning, implementation, resource creation, transport dispatch, live recovery, activation, restart, or changing the original task's status. Approval of this specification alone is not authority to recover the real Episode.

## Current gap and controlling distinction
The current oversee/handoff guidance permits a repeat canonical handoff only after definite first-stage refusal before admission. It also prohibits direct execute or replay when the handoff arrived but callback/execute results are missing. The implementation runs first admission -> factual observation callback -> one execute follow-up as an in-call sequence; returning an uncertain first-stage result does not leave a supported workflow continuation. PRIMECLAW-62 improves future bounded evidence and truthful results but cannot establish missing historical receipts or authorize historical recovery.

Separate two questions: (1) what happened to the OLD request, which can remain unknown, and (2) whether the operator now authorizes ONE NEW bounded continuation of the current work. The latter is not a re-invocation of the old chain and must never claim retrospective non-delivery, a recovered packet, or global exactly-once execution. Historical uncertainty alone must not make this use case unreachable.

## Proposed policy
### Exact owner, current readiness, informed authorization
Apply only to version-2 task-native ownership with the original canonical handoff demonstrably received/completed. Preserve exact owner, selected provider/task, operation, durable Episode/session, worktree, branch, host/placement, original code basis and integration target. No replacement, allocation, rebinding, or generic “resume anything” flow. A changed live route is acceptable only when supported native facts resolve it to that SAME durable session; never guess by name or CWD alone.

The exact owner reads the currently published native task/history, meaningful living plan and accepted bounded focus, code head/publication/worktree facts, available historical observations, and fresh provider-reported Episode and explicitly proven descendant state/actions/queues. Preserve full raw provider fields, null/absence/unknown keys and complete observations through existing bounded native-entry evidence and meaningful bounded reads, not copied full histories in prompts or normal output. Current task/plan changes are judged semantically in editable guidance; compatible updates and unrelated history descendants are not frozen-revision/equality failures. Actual foreign identity, conflicting scope, unsafe current work, unavailable required current evidence or unproved current idleness stops with a useful explanation, not a registry repair.

Present a short factual assessment to the operator: completed handoff; known failed/not-attempted/refused versus unknown historical execute admission; any known callback/partial effects; current Episode report and native idle/empty-queue facts; current task/code progress and accepted next scope; remaining uncertainty and possible prior effects. A receiver report of no separate execute received/pending plus native readiness is useful current evidence, not mathematical proof of historical non-admission. Do not require sender transport IDs, ACKs, retrospective callback proof, a receipt database, or a universal proof of absence when public evidence cannot supply them. The concrete reported TASK-2 case below must be eligible for an informed decision without that impossible prerequisite.

Only an explicit informed operator authorization for this NEW continuation permits sending it. Ordinary conversational authority suffices; no token, approval receipt, special syntax, timestamp ritual or repeated human gate is required. Accept the operator's decision if it already follows the disclosed facts; do not ask again just because a phase ended. Generic “continue” before the uncertainty is disclosed, a model/context change, compaction, unblock alone, idle alone, silence, or an Episode's recommendation is not that authorization. Known pending/running execute or unfinished admitted work is not this recovery case; do not duplicate or cancel it to qualify. Explicit cancellation, terminal disposition or new scope is not silently overridden.

### Continue execute only; do not repeat completed steps
Define a documented owner-led canonical EXECUTE-ONLY continuation through supported existing public/native transport. This is the narrow explicit exception to the current blanket direct-execute prohibition, NOT permission to inject arbitrary chat or reconstruct/replay the old assignment. Deliver one new canonical execute request to the SAME durable Episode with its current native contract, existing accepted bounded focus, exact identity and factual evidence context. It resumes the current work from its durable task/code progress; it does not instruct re-performing historical side effects or restore a stale task/COMMENT snapshot. The Episode remains responsible for semantic reading, implementation and in-scope stopping; the owner does not mirror or rewrite Episode-owned content.

Do not resend handoff, request another compaction as a prerequisite, rerun the historical callback, send initial assignment, call ordinary ralph_handoff, re-enter create/implement as recovery, or make a heartbeat/hook dispatch execute. Compaction remains optional useful context control, never execution authority or a trigger. No new routine permission gate or change to the successful ordinary handoff chain. Existing definite-pre-admission-refusal handling stays distinct. Retained version-1 and initial-creation/assignment recovery are outside this change.

Prefer existing public prompt/follow-up transport, shared canonical editable phase loading, current factual preparation and bounded evidence helpers. Specification does NOT mandate a new tool/endpoint, wire command, protocol, store, scheduler, classifier or recovery state machine. Planning must resolve the smallest supported invocation/mechanical reuse needed to make this a genuinely documented owner operation, not leave the user with an ad hoc raw execute workaround. If the existing public interfaces cannot support the specified outcome, report that concrete constraint for a product decision instead of patching upstream or quietly widening the architecture. A technical choice of helper/adapter is not a new product approval gate.

### Status, factual observations, and stopped outcomes
For a genuinely cleared Blocked task, only its owning Conversation publishes truthful blocker-clearance evidence and In Progress through the selected provider's normal supported lifecycle procedure before the new send. A task already In Progress needs no Blocked round trip. Other lifecycle states follow their existing meaning; this flow does not promote Ready, reopen Done or undo cancellation. Read actual publication/history and prepare only the intended Episode task workspace; preserve unrelated provider/code bytes, staging and history. Publication/preparation failure means no send. No whole-clone clean/equal-head gate or code-level lifecycle classifier replaces LLM judgment.

Record the operator's new decision, accepted focus, current facts and unresolved historical limits in EXISTING provider-native owner-appropriate fields/history. Do not copy Episode Plan/Notes into another authority or use task prose to manufacture a send receipt. The new request must carry the complete current factual context even if the persisted ownership observation is older or a historical callback had partial effects.

After definite native admission of the NEW execute request, use the existing managed factual-observation mechanism to advance only current provider/task/code observations for the unchanged binding. This records the newly admitted continuation's supplied facts, NOT historical callback completion. Do not silently hand-edit ownership JSON or require historical callback/evidence equality. Definite refusal or uncertain new admission does not claim admission or optimistically advance these observations. Keep actual status/preparation/history effects; never roll them back by fiction. If the post-admission factual write fails or may have partial effects, preserve the admitted execute, disclose the actual observation failure and any effects, and inspect before another transition; do not send again or reconstruct the old callback. Observation advancement and transport are not an atomic transaction.

Report once with bounded private-safe native transport/stage/correlation facts where available: requested, definitely admitted (not completed), refused, not attempted, or uncertain, separately from factual-update results. No catch/resend, automatic retry, late-result restart, or inference from missing queues. A new refusal/uncertainty stops THIS authorization; it is not permission for another send. Further disposition requires fresh evidence and a separate informed operator decision under the applicable policy, never a retry loop. A late historical reply cannot trigger or repeat this continuation. Keep unknown historical facts unknown even after a successful new continuation.

## Validation approach and boundaries
Use proportional existing offline Docker/real-client fake-socket/native SDK fixtures with synthetic tasks and sessions; no probe of the real pod-pricing Episode. Show the representative case reaches the informed authorization decision with historical proof genuinely unavailable. After authorization, observe exactly one new canonical execute, no handoff/compaction/initial-assignment resend, preserved bindings, bounded full-evidence access and substantive current-work continuation. Cover definite follow-up failure, unknown historical delivery and callback partial-effect context, plus no authority, known pending work, real scope/identity conflict, Blocked clearance/publication failure, new-send refusal/uncertainty and post-admission factual-write failure. Reuse existing ordinary-handoff, busy-gap and retained-v1 regressions; no exhaustive matrix or framework. Prove what the fixture actually exercises and distinguish SDK/scripted mechanics from daemon/socket/model/live-generation behavior. Run mandated Docker Tier 1 if plugin source changes in later implementation.

Review proposed edits to REQUIREMENTS.md P15, editable oversee/handoff/execute/blocked guidance and directly affected docs so they explicitly state this exception without erasing ordinary no-replay rules. Future accepted changes must update the single maintained requirements source rather than make this task a second requirements list. Native publication/source availability is not proof of loaded code. Any later global activation/full restart/live UAT or actual historical-case recovery needs separate authority and proof of the intended generation; no source copy, /reload or idle observation substitutes.

Non-goals: automatic recovery, historical packet reconstruction/receipt lookup, global exactly-once, generic workflow resume API, task/provider normalization, new durable receipts/evidence store, semantic classifier, upstream Prime Agent changes, auth/model/provider/tier changes, implementation or live tests in this design phase. Leave Done PRIMECLAW-62 and its completed cleanup unchanged. No genuine additional product choice is presently unresolved inside this bounded proposal; if review finds one, surface it rather than deciding wider scope.
